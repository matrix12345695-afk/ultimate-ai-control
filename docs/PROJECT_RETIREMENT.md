# Owner-requested retirement of NOVA and Kinder from ULTIMATE

Scope: the UAC application, its own queue/configuration/menu and active project
records only. Inventory source/configuration/database/processes and independent
Render/GitHub resources are excluded. Owner explicitly requested this cleanup.

An operator activation creates a permanent two-project retirement ledger. New
Telegram commands and old keyboard routes refuse these projects. The keyboard,
project/context lists, help, plan and voice instructions no longer offer them.
Stage16 becomes the planned new commercial AI product. Main's scheduled and
manual HTTP/GitHub monitors filter retired targets. Old schedules and active
context rows are removed; startup reseeding cannot recreate them.

Pending/waiting jobs are cancelled with journal events, pending setup/incident
requests are resolved as owner retirement (not delivery/recovery/approval), and
unconfirmed voice work is rejected. Scoped GitHub approvals are revoked by
explicit request/approval links, never by ambiguous numeric task IDs alone.
SQLite guards cover direct legacy inserts, voice admission and job/schedule
reactivation. Queue admission also rejects retired projects/typed profiles.
The existing owner queue pause, emergency state and model-key deferral remain.

Migration refuses a non-paused queue or running retired job. It is atomic and
repeatable. Local SQLite backups, terminal job/test/report history, accounting
and prior receipts remain historical records; archival modules are retained for
those records and legacy compatibility. This is removal from active management,
not a claim of erasing every historical string, archive or Git commit.

Ten new integration cases cover scoped cancellation and controls, pending vs
delivered receipts, SQL/queue/voice bypass attempts, restart reseeding, all menu
and command routes, zero retired network calls, idempotence, running-job/atomic
failure gates and approval-ID collisions. Existing674 cases retain their old
database fixture behavior until operator activation; new684-case offline suite
passes with18 existing host-dependent skips. Those skips are not fresh sandbox
acceptance. Hosted source checks and actual rollout are separate gates.

The rollout must pin the installed source, verify its clean tracked tree and
Inventory's current PID/source/config metadata, test a restored DB copy, pause
and drain only UAC, stop only its exact worker/dispatcher under their existing
markers, back up/restore-check its DB and apply the tested source/migration.
Owner pauses and independent cron/service definitions must survive unchanged.
Only existing UAC supervisors may resume. A real updated keyboard message and
owner notification need persisted Telegram receipts. Post-activation failure
must keep retired work fenced; do not blindly restore an old monitor-capable
version or overwrite live accounting/history from backup.

Live cleanup/deployment is now verified; see [rollout](PROJECT_RETIREMENT_ROLLOUT.md). Telegram keyboard443 and notice444 have persisted receipts.
An empty ledger is only backward compatibility for older databases/fixtures;
production acceptance requires both retirement rows and their SQL guards.

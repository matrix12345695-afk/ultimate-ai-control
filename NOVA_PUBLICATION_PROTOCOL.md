# NOVA publication protocol: simulator and blocked read-only plan

This increment adds `/nova_deploy`, `/test_nova_deploy` and the Telegram “🧭 План выпуска” button. A queue job reads the exact locked-build CI through an existing contents/actions read-only GitHub App token, runs three independent in-memory simulations, and saves a hashed, immutable readiness report. The report binds NOVA commit a3c3e77e0e74d33241935d25dd3bdfdd306ccd90, Render service srv-dbbhm5k9v7es73f9kf10, workspace tea-d52kjcur433s73ca9810, baseline deploy, before/proposed configuration, lock hash, CI attempt, archive digest, observation hash and expiry. It cannot request or consume an owner approval. Source and report references are checked again when displayed through evidence memory and Plan 4.0.

## What is actually executed

The installed broker reads GitHub only. It does not load a Render credential or issue any Render HTTP request. Live SQLite receives a publication-plan row and normal job/event/notification/memory records. Simulation approvals and state-machine journals exist only in separate `:memory:` SQLite databases and never in the live control database. A private 0600 policy pins the protocol definition hash and requires `mode=dry_run_only`.

Three synthetic scenarios exercise successful publication, conditional rollback, and an accepted write whose response is lost. They do not prove a live Render publication or rollback. 24 additional machine tests cover concurrent reservations, restart after a lost response, stale scope, revocation, exact service/commit/config binding, readback after configuration ACK, bounded reads, mismatched deploy IDs, failed build without cutover, conditional rollback expiry and failed rollback. Nine integration tests cover read-only scope, immutable storage, invalid evidence, memory invalidation, queue notices and commit gaps. Existing 83-check hosted Node/PostgreSQL/Chromium evidence remains a separate real CI result.

## Protocol design, not a live provider adapter

The fixture-only durable machine journals a mutation intent under a SQLite write lock before calling its synthetic provider. Only one worker reserves that transition. Missing/uncertain write responses and expired intent leases enter `ambiguous`; automatic write retry is forbidden. A known deploy ID may be polled with bounded read retries. Platform and repository scope are rechecked before every simulated mutation. Configuration ACK alone is insufficient: a separate readback must match. Three failed HTTP checks permit only the explicitly scoped baseline rollback; a failed rollback terminates without recursion. Initial approval is valid for at most 15 minutes, the explicitly authorized conditional recovery window for at most one hour; revocation blocks recovery too. Only the exact FixtureRender class is accepted; real clients are rejected before any provider method.

The real platform observation is a timestamped, committed snapshot collected through read-only connectors. Reports mark it stale after 15 minutes and explain that `/test_nova_deploy` refreshes CI and calculation, not Render. A 20-deploy sample is not a complete queue proof. Production CRM backup/restore evidence, retained baseline build eligibility, provider access, an audited live adapter and exact owner release approval are all missing, so every report remains blocked and `publish_allowed=false`, `may_request_approval=false`, `published=false`, `production_mutations=0`.

Official documentation: https://render.com/docs/deploys , https://render.com/docs/health-checks , https://render.com/docs/rollbacks . API reference pages returned HTTP 403 in this environment. Payload shapes were checked against official render-oss/cli generated sources at fa6219b4a167ff3094deafef2209f8a33bf670ed (`pkg/client/client.gen.go` and `types.gen.go`; original source blob IDs 56d8888cddefe4cbbc7703b083c01742584d83a2 and 2d391fa75307ae646ca996f078f5329042cc4e54). No upstream SDK is installed or vendored.

Proposed restricted writes: PATCH `/services/{id}` for autoDeployTrigger=off, healthCheckPath=/health and the exact npm-ci build command; POST `/services/{id}/deploys` with exact commitId; POST `/services/{id}/rollback` with baseline deployId. The API commit/rollback endpoints do not themselves turn off auto deploy. No API idempotency guarantee was observed. A rollback uses retained build artifacts and does not restore databases, persistent disks or external writes; current environment/configuration may differ from the target build. The simulator does not claim otherwise.

## Isolation and rollback

Only ULTIMATE reporting is eligible for this increment's deployment. Its installer backs up and restores a test copy of its own database, runs tests with existing private sandbox/Node policy, checks a restored-copy report and evidence invalidation, installs its own policy, and restarts only its own worker/dispatcher. It verifies Inventory process/file/config metadata, unchanged approval/candidate counts, deferred model setup and zero paid provider records. Its exact-version rollback returns to UAC 95b172f38cfefe93e9dd31c2ebcf027f65a50940, drains UAC jobs and cancels only unsupported queued nova-deploy-plan-v1 jobs, preserving owner pauses and historical records. This is not a Render rollback. No hourly coding automation is added. Stage 9 remains active with this verified subtask recorded after deployment.
